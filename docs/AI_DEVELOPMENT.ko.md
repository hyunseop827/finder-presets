# Finder Presets를 만든 과정

[English](AI_DEVELOPMENT.md)

Finder Presets는 한 사람이 AI 코딩 에이전트와 함께 만든 앱입니다. 앱이 무엇을 하고 어떻게 느껴져야 하는지, 어디까지가
내보낼 만한 품질인지는 제가 정했고, 코드·테스트·문서의 대부분은 그 방향에 따라 에이전트(주로
[Claude Code](https://claude.com/claude-code))가 작성했습니다. 이 문서는 그 방식을 설명합니다. 과정도 코드만큼 이
프로젝트의 일부이기 때문입니다.

## 누가 무엇을 했나

| 저 | 에이전트 |
|---|---|
| 풀 문제를 정함: Finder 보기 하나를 백그라운드 앱 없이 어디에나 적용하기 | Finder의 `.DS_Store` 형식과 DSStore 라이브러리를 읽고 엔진을 만듦 |
| 요구사항을 한국어로, 대화 하나씩 씀 | 그것을 작은 단계의 계획·코드·테스트로 바꿈 |
| 제품 결정을 모두 내림 (단축키 동작, 오류 문구, 아이콘, README) | 장단점과 함께 선택지를 내고 하나를 추천함 |
| 에이전트가 준비한 체크리스트로 실제 Finder에서 테스트함 | 테스트 폴더와 체크리스트를 준비하고, 결과를 확인한 뒤 흔적을 지움 |
| 언제 내보낼지 정함: 제 승인("올려") 없이는 아무것도 나가지 않음 | 버전과 릴리스 노트를 준비하고 "올려"라고 해야 내보냄. 태그와 공개는 직접 하지 않음 (CI가 함) |

## 작업 방식

1. **요청.** 평범한 한국어로 요청합니다("단축키를 가끔 두 번 눌러야 돼요, 확인해 주세요").
2. **바꾸기 전에 조사.** 에이전트가 `~/FinderPresets-Test`의 테스트 폴더와 따로 둔 데이터 폴더에서 문제를 재현합니다.
   실제 프리셋과 기록은 건드리지 않습니다.
3. **작은 단계로 변경.** 단계마다 전체 테스트를 돌립니다.
4. **사용자처럼 확인.** 로직은 단위 테스트로, 실제 창은 debug 전용 *레이아웃 검사*로(두 언어, 라이트·다크), 앱 흐름은
   *셀프 테스트*로 확인합니다. 실제 Finder가 필요한 것(재시작, ⌃⌥⌘P 단축키)은 에이전트가 모두 준비해 둔 뒤 제가 한
   번에 체크리스트로 확인합니다.
5. **반박하는 리뷰.** 큰 작업에서는 여러 에이전트가 영역을 나눠(엔진, 앱 상태, 화면·번역, CLI·CI, 안 쓰는 코드, 테스트)
   동시에 리뷰하고, 다른 에이전트가 각 지적을 반박해 본 뒤에야 고칩니다. 최근 리뷰에서는 56개가 나와 55개가 확인됐고,
   다섯 묶음으로 나눠 고치면서 묶음마다 전체 테스트를 통과시켰습니다.
6. **CI로 릴리스.** 앱을 바꾸면 에이전트가 `Info.plist`의 버전을 올리고 릴리스 노트를 씁니다. 제가 "올려"라고 하면
   커밋하고 풀 리퀘스트를 열어, CI를 통과하면 머지합니다. 그러면 `main`의 CI가 DMG 빌드, 태그, 공개를 하고 README의
   내려받기 링크로 다시 받아 확인합니다. 태그와 공개를 에이전트가 직접 하지는 않습니다.

에이전트가 따르는 규칙은 [AGENTS.md](../AGENTS.md)에 적어 두어서, 어떤 에이전트든 이어서 작업할 수 있습니다.

## 이 과정에서 나온 결정들

- **쓰기 전에 Finder를 종료.** 테스트해 보니 Finder는 종료할 때 열린 창의 보기 상태를 기록해서 방금 쓴 `.DS_Store`를
  덮어썼습니다. 그래서 순서를 정했습니다: 창 읽기 → 종료 → 쓰기 → 실행 → 창 다시 열기 → 안정될 때까지 대기 → 다시 읽기.
- **빠른 적용은 창이 보여 주는 값을 읽음.** Finder는 보기 변경을 늦게 기록해서 디스크의 값이 오래됐을 수 있습니다.
  단축키는 앞 창의 현재 보기를 직접 묻고, 다를 때만 Finder를 다시 시작합니다.
- **백그라운드 프로세스 없음.** 단축키는 macOS 서비스라서 쓰기 전에는 아무것도 돌지 않습니다. 단축키는 시스템 설정에서만
  지정할 수 있어서, 앱이 단계별 안내를 보여 줍니다. 처음에는 저절로 넘어가는 방식이었는데, 이전/다음으로만 움직이도록
  제가 바꿔 달라고 했습니다.
- **Finder 창 복원.** 스크립트로 종료한 Finder는 창을 복원하지 않아서, 앱이 다시 시작한 뒤 열려 있던 창을 다시 엽니다.
- **안전한 범위.** `/`, `/Users`, 홈 폴더보다 위쪽은 거부합니다(시스템 볼륨은 읽기 전용입니다). 모든 변경은 쓰기 전에
  백업하고, 기록은 폴더에 쓰기 전에 먼저 남겨서 되돌리기가 항상 닿습니다.
- **조용한 창.** 툴바의 버튼 세 개를 상태 막대의 글자 링크로 바꿨습니다(기록 · 사용법 · 업데이트 확인).
- **아이콘 여러 시안.** 코드로 그린 시안을 여러 번 Dock·Finder 크기로 비교해 두 가지 파란색의 폴더를 골랐고, Apple의
  Finder 얼굴은 일부러 쓰지 않았습니다.
- **버전 번호로 릴리스.** 제 다른 앱 [Menu Pulse](https://github.com/hyunseop827/menu-pulse)와 같은 방식입니다.
- **앱 안에서 업데이트(0.3.0).** Sparkle이 하루 한 번, 그리고 업데이트 확인…을 누를 때 릴리스의 업데이트 목록을 확인하고, 설치는 고를 때만 합니다. 모든 업데이트는 개인 키를 저만 가진 EdDSA 키로 확인합니다. 임시 서명(ad-hoc) 앱이 스스로 업데이트하고 다시 열리며 Gatekeeper가 다시 묻지 않는 것은 이 Mac에서 로컬 테스트로 확인했지만, 그 시험은 앱의 hardened runtime과 하루 한 번 확인을 끈 설정이었습니다. 이 버전이 쓰는 설정으로는 아직 그렇게 확인하지 않았습니다.

## 숫자로 보면

- 엔진, 앱 모델, CLI를 합쳐 단위 테스트 249개, 푸시마다 CI.
- 고정 창, 모든 시트, 상태 막대를 한국어·영어, 라이트·다크로 확인하는 레이아웃 검사.
- Finder를 건드리지 않고 가져오기 → 적용 → 되돌리기 → 편집기 → 서비스 → 빠른 적용을 돌리는 셀프 테스트.
- #2까지의 커밋에는 `Co-Authored-By: Claude` 줄이 있었고, 그 뒤의 커밋에는 없습니다(#4에서 그 규칙을 없애고,
  README의 AI 안내 한 곳에만 적습니다).

## 이 방식이 중요한 이유

에이전트는 사람이 읽는 것보다 빠르게 코드를 씁니다. 그래서 이 프로젝트의 품질은 그 주변의 고리에서 나옵니다: 정확한
요청, 작은 변경, 단계마다 테스트, 반박하는 리뷰, 사람이 하는 실제 확인. 사람의 시간은 대부분 타이핑이 아니라 결정과
확인에 쓰였습니다.
